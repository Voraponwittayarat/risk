เอกสารนี้เป็นบันทึกแผนพัฒนากระบวนการทบทวนความเสี่ยง, RCA, CAPA และ Risk Register ของ RiskHRMS เพื่อให้ผู้พัฒนาและ AI ที่รับช่วงต่อดำเนินงานตามหลักการเดียวกัน โดยอ้างอิง `docs/RISK-REVIEW-AND-RISK-REGISTER-PRINCIPLES-TH.md`

## 1. เป้าหมายของระบบ

ระบบต้องช่วยให้หน่วยงานเริ่มทบทวนเหตุการณ์ได้ทันที โดยไม่ต้องรอ RM และต้องเชื่อมการเรียนรู้จากเหตุการณ์ไปสู่การปรับระบบอย่างต่อเนื่องตามวงจรนี้

```text
ยืนยันว่าเป็นความเสี่ยง
  → หน่วยงานทบทวนข้อเท็จจริงและจัดการเบื้องต้น
  → เลือกระดับการทบทวน/RCA ที่เหมาะสม
  → กำหนดมาตรการ CAPA และวิธีวัดผล
  → บรรจุหรือเชื่อม Risk Register
  → ติดตามการดำเนินการและประสิทธิผล
  → ประเมิน Residual Risk
  → ปิด ลดระดับ ยกระดับ หรือทบทวนรอบถัดไป
```

หลักสำคัญ:

- หน่วยงานเจ้าของเรื่องเริ่มทบทวนได้เองตั้งแต่วันเกิดเหตุ
- RCA สามารถจบที่หน่วยงานได้ หากขอบเขตปัญหาและอำนาจแก้ไขอยู่ภายในหน่วยงาน
- PCT เป็นหนึ่งในทีมที่อาจเข้าร่วม ไม่ใช่ทีมเดียว ระบบต้องรองรับทีมนำและทีมคร่อมสายงานหลายประเภท
- RM ทำหน้าที่กำกับมาตรฐาน มองภาพรวม และช่วยกรณีซับซ้อน โดยไม่เป็นคอขวดของทุกเหตุการณ์
- RCA ที่สรุปแล้วต้องเชื่อมไปยัง Risk Register และมาตรการต้องมีเจ้าของ กำหนดเวลา หลักฐาน และเกณฑ์วัดผล
- ความเสี่ยงสำคัญยังต้องติดตามต่อได้ แม้ไม่มี Incident ใหม่

## 4. แผนพัฒนาระยะที่ 1: ผู้ร่วมทบทวนและ Voice of Staff

เป้าหมาย: ทำให้เห็นว่าใครเป็นเจ้าของเรื่อง ใครร่วมให้ข้อมูล และใครช่วยวิเคราะห์ โดยไม่โยนงานทั้งหมดให้ RM

### 4.1 โครงสร้างข้อมูล

- [ ] เพิ่มผู้ร่วมทบทวนแบบหลายรายการต่อ RCA
- [ ] ระบุประเภทผู้ร่วมทบทวน: บุคคล, หน่วยงาน, ทีมนำ/ทีมคร่อมสายงาน หรือผู้เชี่ยวชาญเฉพาะเรื่อง
- [ ] ระบุบทบาท เช่น เจ้าของเรื่อง, ผู้ดำเนินการทบทวน, ผู้ให้ข้อมูล, ผู้ช่วยวิเคราะห์, ผู้รับรองข้อสรุป
- [ ] เก็บสถานะการตอบรับและเวลาที่เข้าร่วม โดยไม่บังคับให้ทุกคนต้องอนุมัติก่อนหน่วยงานดำเนินงานต่อ
- [ ] เพิ่มบันทึก Voice of Staff แยกตามการสัมภาษณ์ โดยเก็บประเด็นสำคัญ สภาพงานจริง และข้อเสนอแนะ
- [ ] บันทึก audit trail เมื่อเพิ่ม ลบ หรือเปลี่ยนบทบาทผู้ร่วมทบทวน

### 4.2 UX/UI

- [ ] เพิ่มส่วน “ทีมทบทวนเรื่องนี้” ที่เห็นเจ้าของเรื่องเป็นคนแรก
- [ ] มีปุ่ม “ขอทีมอื่นช่วย” พร้อมเลือกวัตถุประสงค์ เช่น ช่วยวิเคราะห์กระบวนการ ให้ความเห็นเฉพาะด้าน หรือร่วมกำหนดมาตรการ
- [ ] แสดงว่าแต่ละทีมมีหน้าที่อะไร เพื่อลดความเข้าใจว่าเป็นการส่งมอบความรับผิดชอบ
- [ ] เพิ่มแบบบันทึกการสัมภาษณ์สั้น กระชับ และใช้ภาษาที่ไม่กล่าวโทษบุคคล
- [ ] แสดงข้อมูลที่ยังขาดก่อนนัดทบทวนหรือสรุป RCA

### 4.3 เกณฑ์รับงาน

- หน่วยงานสามารถเริ่มและดำเนินการ RCA ได้โดยไม่มี RM อยู่ในรายชื่อ
- RCA หนึ่งรายการมีผู้ร่วมทบทวนจากหลายหน่วยงานหรือหลายทีมได้
- ผู้ใช้เห็นเจ้าของเรื่องและบทบาทของทุกคนอย่างชัดเจน
- Voice of Staff เชื่อมกับ RCA แต่ไม่ปะปนกับข้อสรุปสาเหตุจนกว่าจะผ่านการวิเคราะห์

## 5. แผนพัฒนาระยะที่ 2: จบที่หน่วยงานหรือยกระดับ

เป้าหมาย: ให้ระบบช่วยเลือกเส้นทางที่เหมาะสมกับความซับซ้อนและระดับความเสี่ยง

### 5.1 ผลลัพธ์หลังหน่วยงานทบทวน

- [ ] เพิ่มผลลัพธ์ “จัดการและจบที่หน่วยงาน”
- [ ] เพิ่มผลลัพธ์ “ติดตามมาตรการต่อในหน่วยงาน”
- [ ] เพิ่มผลลัพธ์ “ขอทีมคร่อมสายงานร่วมทบทวน”
- [ ] เพิ่มผลลัพธ์ “ยกระดับเป็น RCA ระดับองค์กร”
- [ ] บันทึกเหตุผลของเส้นทางที่เลือกและผู้ตัดสินใจ

### 5.2 เงื่อนไขช่วยแนะนำการยกระดับ

ระบบควรแนะนำ แต่ไม่ตัดสินแทนผู้รับผิดชอบ เมื่อพบเงื่อนไขต่อไปนี้:

- เหตุรุนแรงหรือมีโอกาสเกิดผลกระทบรุนแรง
- เหตุซ้ำหรือแนวโน้มเพิ่มขึ้น
- ปัญหาครอบคลุมหลายหน่วยงานหรือหลายกระบวนการ
- หน่วยงานไม่มีอำนาจ ทรัพยากร หรือความเชี่ยวชาญเพียงพอในการแก้ไข
- เป็นความเสี่ยงเชิงระบบหรือเกี่ยวข้องกับนโยบายระดับโรงพยาบาล
- มาตรการเดิมไม่ได้ผล

### 5.3 เกณฑ์รับงาน

- งานที่จบในหน่วยงานไม่ต้องรอ RM กดอนุมัติทุกขั้น
- การขอทีมช่วยไม่เปลี่ยนเจ้าของความเสี่ยงโดยอัตโนมัติ
- ผู้บริหารและ RM เห็นเหตุผลการยกระดับและงานที่ไม่มีผู้รับผิดชอบ
- ไม่มีสถานะกำกวม เช่น “รอทีมรับ” โดยไม่บอกว่าทีมใดต้องทำอะไร

## 6. แผนพัฒนาระยะที่ 3: ปรับแบบฟอร์ม RCA ให้ใช้ง่าย

เป้าหมาย: ลดความยาวและภาระการกรอก โดยยังรักษาคุณภาพการวิเคราะห์

- [ ] เปลี่ยนเมนูลัดเป็น stepper ที่บอกสถานะ: ยังไม่เริ่ม, กำลังทำ, ข้อมูลครบ และต้องแก้ไข
- [ ] แบ่งการทำงานเป็นขั้นแทนการแสดงทุกส่วนในหน้ายาวหน้าเดียว
- [ ] ใช้ progressive disclosure แสดงเฉพาะเครื่องมือวิเคราะห์ที่จำเป็น
- [ ] ให้ผู้ใช้เลือกระดับการทบทวน: ทบทวนด่วน, ทบทวนหลายเหตุการณ์ หรือทบทวนเชิงลึก
- [ ] เพิ่ม autosave พร้อมเวลา “บันทึกล่าสุด” และแจ้งเมื่อมีข้อมูลที่ยังไม่บันทึก
- [ ] แสดงรายการข้อมูลที่ขาดพร้อมลิงก์ไปยังช่องที่ต้องแก้
- [ ] ปรับคำศัพท์ให้เป็นภาษาไทยที่เข้าใจง่าย และแสดงคำอังกฤษเป็นคำอธิบายรอง
- [ ] รองรับ mobile และหน้าจอขนาดเล็กสำหรับการทบทวนหน้างาน

เกณฑ์รับงาน: ผู้ใช้สามารถทำร่าง กลับมาทำต่อ และทราบขั้นตอนถัดไปได้โดยไม่ต้องเลื่อนหาส่วนที่เกี่ยวข้องเอง

## 7. แผนพัฒนาระยะที่ 4: ติดตาม CAPA และประสิทธิผล

เป้าหมาย: แยกให้ชัดระหว่าง “ทำมาตรการแล้ว” กับ “มาตรการได้ผล”

- [ ] หน้ารวม CAPA ของฉัน/หน่วยงาน พร้อมสถานะใกล้ครบกำหนดและเกินกำหนด
- [ ] เพิ่มหลักฐานการดำเนินการและผู้ยืนยันการนำมาตรการไปใช้
- [ ] บันทึกค่าหลังปรับปรุงเทียบ Baseline และ Target
- [ ] สรุปผลเป็น ได้ผล, ได้ผลบางส่วน, ไม่ได้ผล หรือข้อมูลยังไม่พอ
- [ ] รองรับการแก้ไขมาตรการโดยเก็บ revision และประวัติเดิม
- [ ] เมื่อไม่ได้ผล ให้สร้างมาตรการใหม่ เปิดการทบทวนเพิ่ม หรือยกระดับได้
- [ ] แสดงเหตุการณ์ซ้ำที่เกี่ยวข้องในช่วงติดตาม
- [ ] แจ้งเตือนเจ้าของมาตรการก่อนครบกำหนด โดยไม่ส่งทุกงานให้ RM

เกณฑ์รับงาน: ระบบห้ามปิดความเสี่ยงเพียงเพราะบันทึกว่าทำ CAPA เสร็จ ต้องมีผลการประเมินประสิทธิผลหรือเหตุผลที่ได้รับอนุมัติ

## 8. แผนพัฒนาระยะที่ 5: วงรอบ Risk Register

เป้าหมาย: ให้ Risk Register เป็นทะเบียนความเสี่ยงที่มีชีวิต ไม่ใช่รายชื่อที่สร้างจาก Incident เท่านั้น

- [ ] ประเมิน Current/Residual Risk หลังใช้มาตรการ
- [ ] กำหนดเจ้าของความเสี่ยง รอบทบทวน และวันทบทวนครั้งถัดไป
- [ ] ติดตามความเสี่ยงสำคัญต่อได้แม้ไม่มี Incident ใหม่
- [ ] แสดง Incident, Near Miss, Proactive Risk และ RCA ที่เชื่อมกับความเสี่ยงเดียวกัน
- [ ] รองรับผลการทบทวน: คงระดับ, ลดระดับ, ยกระดับ, ปิดแบบเฝ้าระวัง หรือเปิดกลับมาใหม่
- [ ] เก็บเหตุผลและหลักฐานประกอบการเปลี่ยนสถานะทุกครั้ง
- [ ] ป้องกันการสร้าง Risk Register ซ้ำจาก NRLS และ scope เดียวกัน

เกณฑ์รับงาน: เจ้าของความเสี่ยงสามารถตอบได้ว่าความเสี่ยงลดลงหรือไม่ ใช้หลักฐานอะไร และต้องทบทวนอีกเมื่อใด

## 9. แผนพัฒนาระยะที่ 6: RCA Command Center และ Decision Support

เป้าหมาย: เปลี่ยนหน้ารวมจากตัวนับงานเป็นหน้าช่วยตัดสินใจ

- [ ] แยกมุมมองงานของฉัน, งานของหน่วยงาน, งานที่ร่วมกับทีมอื่น และภาพรวมองค์กรตามสิทธิ
- [ ] แสดง RCA ค้าง, CAPA ค้าง, รอประเมินผล, Risk Register ถึงรอบ และมาตรการไม่ได้ผล
- [ ] แสดงความเสี่ยงรุนแรง ความเสี่ยงเพิ่มขึ้น เหตุซ้ำ และหน่วยงานที่ควรได้รับการสนับสนุน
- [ ] แสดง Near Miss และ Proactive Risk แยกจาก Incident ที่เกิดผลกระทบแล้ว
- [ ] แก้ KPI ที่ตีความผิด เช่นจำนวน “ทบทวนแล้ว” ที่ไม่สอดคล้องกับรายการจริง
- [ ] ใช้สถานะและตัวเลขชุดเดียวกันระหว่าง Incident, RCA, CAPA และ Risk Register
- [ ] ทุกการ์ดต้องกดดูรายการต้นทางได้ และ filter ต้องใช้ข้อมูลจริง ไม่ใช้ mockup

## 10. แผนพัฒนาระยะที่ 7: ความปลอดภัยในการเชื่อมข้อมูล

- [ ] เมื่อพบ Risk Register หลายรายการที่ NRLS เดียวกัน ต้องให้ผู้ใช้เลือกและยืนยัน ห้ามเลือกผิดโดยอัตโนมัติ
- [ ] แสดง scope, หน่วยงาน, เจ้าของ และสถานะของ Risk Register ก่อนเชื่อม
- [ ] ตรวจสิทธิ์การเชื่อมระดับหน่วยงานและระดับโรงพยาบาลที่ backend
- [ ] ทำ completion endpoint ให้ idempotent เพื่อป้องกันการกดซ้ำหรือ request ซ้ำ
- [ ] จัดการ concurrent creation เพื่อไม่ให้เกิด Risk Register ซ้ำจาก unique constraint race
- [ ] ใช้ transaction กับการสรุป RCA, เชื่อม Risk Register, เชื่อม CAPA และ audit trail
- [ ] เพิ่ม integration test สำหรับ create/link/complete/retry และ permission boundary

## 11. สถานะหลักที่ควรใช้ร่วมกัน

ชื่อที่แสดงกับผู้ใช้อาจเป็นภาษาไทย แต่ค่าภายในควรสม่ำเสมอและแปลงจากจุดเดียว

### RCA

```text
DRAFT → IN_PROGRESS → READY_TO_COMPLETE → COMPLETED
                           ↘ NEEDS_SUPPORT / ESCALATED
CANCELLED ใช้เมื่อยกเลิกพร้อมเหตุผล
```

### CAPA

```text
PENDING → IN_PROGRESS → IMPLEMENTED → EFFECTIVENESS_DUE
                                    → EFFECTIVE → CLOSED
                                    → PARTIALLY_EFFECTIVE → REVISED
                                    → NOT_EFFECTIVE → REVISED / ESCALATED
```

### Risk Register

```text
OPEN → MONITORING → CONTROLLED → CLOSED_MONITORING
                    ↘ ESCALATED
CLOSED_MONITORING สามารถ REOPEN ได้เมื่อเกิดเหตุซ้ำหรือระดับความเสี่ยงเพิ่ม
```

ก่อนนำ state model ไปใช้ ต้องตรวจ mapping กับข้อมูลเดิมและสร้าง migration ที่ไม่ทำให้ประวัติสูญหาย

## 12. ข้อกำหนดร่วมทุกระยะ

- รักษาข้อมูลผู้ป่วยและข้อมูล Incident เป็นข้อมูลอ่อนไหว
- ทุก API ต้องตรวจ role และ department scope ที่ backend
- เก็บ audit trail สำหรับการเปลี่ยนเจ้าของ สถานะ การส่งต่อ การสรุป และการปิด
- ไม่ลบประวัติ RCA/CAPA เพื่อแก้ข้อมูลย้อนหลัง ให้ใช้ revision หรือสถานะยกเลิกพร้อมเหตุผล
- ทุก filter, counter และ dashboard ต้องมาจากข้อมูลจริง
- รองรับข้อมูลเก่าและระบุแผน migration/backfill ก่อนเพิ่ม field บังคับ
- ห้ามใช้ `prisma db push` บน production
- migration production ใช้ `prisma migrate deploy` ผ่าน updater เท่านั้น
- ก่อน deploy ที่มี migration ต้องมี backup พร้อม SHA-256

## 13. วิธีดำเนินงานแต่ละรอบ

1. อ่าน `AGENTS.md`, เอกสารหลักการ และไฟล์นี้
2. ตรวจ `git status`, branch และ `origin/main`; รักษางานที่ยังไม่ commit ของผู้อื่น
3. สร้าง feature branch ชื่อขึ้นต้นด้วย `codex/`
4. เลือกพัฒนาครั้งละหนึ่ง vertical slice ที่ใช้งานได้ตั้งแต่ UI → API → database → audit
5. เพิ่ม test เฉพาะพฤติกรรมสำคัญ เช่น permission, transition, transaction และการกดซ้ำ
6. รัน `npm run build` ใน `frontend` และ `backend`
7. ตรวจ migration และ `git diff --check`
8. commit, merge เข้า `main` และ push GitHub
9. ให้ production auto-deploy จาก `origin/main`; ห้ามแก้ source บน server
10. ตรวจ backup, running commit, migration, service, `/health` และหน้าที่เปลี่ยนแบบ read-only

## 14. ลำดับงานถัดไปที่แนะนำ

เริ่มจาก vertical slice ต่อไปนี้:

1. **ผู้ร่วมทบทวนหลายทีมและ Voice of Staff**
2. **ผลลัพธ์จบที่หน่วยงานหรือขอทีมคร่อมสายงานช่วย**
3. **ปรับ RCA form เป็น stepper พร้อม completeness และ autosave**
4. **ประเมินประสิทธิผล CAPA และ Residual Risk**
5. **ปรับ RCA Command Center เป็น Decision Support**

เหตุผลที่เริ่มข้อ 1–2 ก่อน: เป็นกลไกสำคัญที่ทำให้หน่วยงานเริ่มทบทวนและจบงานได้เอง พร้อมขอความช่วยเหลือจากทีมที่เหมาะสม โดยไม่ทำให้ RM กลับมาเป็นคอขวด
