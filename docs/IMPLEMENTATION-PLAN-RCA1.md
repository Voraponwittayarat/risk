## 1. เป้าหมายของระบบ

ระบบต้องช่วยให้หน่วยงานเริ่มทบทวนเหตุการณ์ได้ทันที โดยไม่ต้องรอ RM และต้องเชื่อมการเรียนรู้จากเหตุการณ์ไปสู่การปรับระบบอย่างต่อเนื่องตามวงจรนี้

```text
ยืนยันว่าเป็นความเสี่ยง
  → หน่วยงานทบทวนข้อเท็จจริงและจัดการเบื้องต้น
  → เลือกระดับการทบทวน/RCA ที่เหมาะสม
  → กำหนดมาตรการ CAPA และวิธีวัดผล
  → บรรจุหรือเชื่อม Risk Register
  → ติดตามการดำเนินการและประสิทธิผล
  → ประเมิน Residual Risk
  → ปิด ลดระดับ ยกระดับ หรือทบทวนรอบถัดไป
```

หลักสำคัญ:

- หน่วยงานเจ้าของเรื่องเริ่มทบทวนได้เองตั้งแต่วันเกิดเหตุ
- RCA สามารถจบที่หน่วยงานได้ หากขอบเขตปัญหาและอำนาจแก้ไขอยู่ภายในหน่วยงาน
- PCT เป็นหนึ่งในทีมที่อาจเข้าร่วม ไม่ใช่ทีมเดียว ระบบต้องรองรับทีมนำและทีมคร่อมสายงานหลายประเภท
- RM ทำหน้าที่กำกับมาตรฐาน มองภาพรวม และช่วยกรณีซับซ้อน โดยไม่เป็นคอขวดของทุกเหตุการณ์
- RCA ที่สรุปแล้วต้องเชื่อมไปยัง Risk Register และมาตรการต้องมีเจ้าของ กำหนดเวลา หลักฐาน และเกณฑ์วัดผล
- ความเสี่ยงสำคัญยังต้องติดตามต่อได้ แม้ไม่มี Incident ใหม่

## 5. แผนพัฒนาระยะที่ 2: จบที่หน่วยงานหรือยกระดับ

เป้าหมาย: ให้ระบบช่วยเลือกเส้นทางที่เหมาะสมกับความซับซ้อนและระดับความเสี่ยง

### 5.1 ผลลัพธ์หลังหน่วยงานทบทวน

- [x] เพิ่มผลลัพธ์ “จัดการและจบที่หน่วยงาน”
- [x] เพิ่มผลลัพธ์ “ติดตามมาตรการต่อในหน่วยงาน”
- [x] เพิ่มผลลัพธ์ “ขอทีมคร่อมสายงานร่วมทบทวน”
- [x] เพิ่มผลลัพธ์ “ยกระดับเป็น RCA ระดับองค์กร”
- [x] บันทึกเหตุผลของเส้นทางที่เลือกและผู้ตัดสินใจ

### 5.2 เงื่อนไขช่วยแนะนำการยกระดับ

ระบบควรแนะนำ แต่ไม่ตัดสินแทนผู้รับผิดชอบ เมื่อพบเงื่อนไขต่อไปนี้:

- เหตุรุนแรงหรือมีโอกาสเกิดผลกระทบรุนแรง
- เหตุซ้ำหรือแนวโน้มเพิ่มขึ้น
- ปัญหาครอบคลุมหลายหน่วยงานหรือหลายกระบวนการ
- หน่วยงานไม่มีอำนาจ ทรัพยากร หรือความเชี่ยวชาญเพียงพอในการแก้ไข
- เป็นความเสี่ยงเชิงระบบหรือเกี่ยวข้องกับนโยบายระดับโรงพยาบาล
- มาตรการเดิมไม่ได้ผล

### 5.3 เกณฑ์รับงาน

- งานที่จบในหน่วยงานไม่ต้องรอ RM กดอนุมัติทุกขั้น
- การขอทีมช่วยไม่เปลี่ยนเจ้าของความเสี่ยงโดยอัตโนมัติ
- ผู้บริหารและ RM เห็นเหตุผลการยกระดับและงานที่ไม่มีผู้รับผิดชอบ
- ไม่มีสถานะกำกวม เช่น “รอทีมรับ” โดยไม่บอกว่าทีมใดต้องทำอะไร

## 8. แผนพัฒนาระยะที่ 5: วงรอบ Risk Register

- [x] กำหนดเจ้าของความเสี่ยง รอบทบทวน และวันทบทวนครั้งถัดไป
- [x] ติดตามความเสี่ยงสำคัญต่อได้แม้ไม่มี Incident ใหม่
- [x] แสดง Incident, Near Miss, Proactive Risk และ RCA ที่เชื่อมกับความเสี่ยงเดียวกัน
- [x] รองรับผลการทบทวน: คงระดับ, ลดระดับ, ยกระดับ, ปิดแบบเฝ้าระวัง หรือเปิดกลับมาใหม่

## 11. สถานะหลักที่ควรใช้ร่วมกัน

ชื่อที่แสดงกับผู้ใช้อาจเป็นภาษาไทย แต่ค่าภายในควรสม่ำเสมอและแปลงจากจุดเดียว

### RCA

```text
DRAFT → IN_PROGRESS → READY_TO_COMPLETE → COMPLETED
                           ↘ NEEDS_SUPPORT / ESCALATED
CANCELLED ใช้เมื่อยกเลิกพร้อมเหตุผล
```

### CAPA

```text
PENDING → IN_PROGRESS → IMPLEMENTED → EFFECTIVENESS_DUE
                                    → EFFECTIVE → CLOSED
                                    → PARTIALLY_EFFECTIVE → REVISED
                                    → NOT_EFFECTIVE → REVISED / ESCALATED
```

### Risk Register

```text
OPEN → MONITORING → CONTROLLED → CLOSED_MONITORING
                    ↘ ESCALATED
CLOSED_MONITORING สามารถ REOPEN ได้เมื่อเกิดเหตุซ้ำหรือระดับความเสี่ยงเพิ่ม
```

ก่อนนำ state model ไปใช้ ต้องตรวจ mapping กับข้อมูลเดิมและสร้าง migration ที่ไม่ทำให้ประวัติสูญหาย

## 12. ข้อกำหนดร่วมทุกระยะ

- รักษาข้อมูลผู้ป่วยและข้อมูล Incident เป็นข้อมูลอ่อนไหว
- ทุก API ต้องตรวจ role และ department scope ที่ backend
- เก็บ audit trail สำหรับการเปลี่ยนเจ้าของ สถานะ การส่งต่อ การสรุป และการปิด
- ไม่ลบประวัติ RCA/CAPA เพื่อแก้ข้อมูลย้อนหลัง ให้ใช้ revision หรือสถานะยกเลิกพร้อมเหตุผล
- ทุก filter, counter และ dashboard ต้องมาจากข้อมูลจริง
- รองรับข้อมูลเก่าและระบุแผน migration/backfill ก่อนเพิ่ม field บังคับ
- ห้ามใช้ `prisma db push` บน production
- migration production ใช้ `prisma migrate deploy` ผ่าน updater เท่านั้น
- ก่อน deploy ที่มี migration ต้องมี backup พร้อม SHA-256
