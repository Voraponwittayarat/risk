# นำเข้าความเสี่ยงด้านยาจาก CSV

เมนู **นำเข้าความเสี่ยงด้านยา** เปิดให้ Admin (`admin`) และคณะกรรมการบริหารความเสี่ยงระดับโรงพยาบาล (`rm_committee` + `rmScope=hospital`)
RM ระดับหน่วยงาน/กลุ่มงาน หัวหน้าหน่วยงาน และเจ้าหน้าที่ไม่สามารถใช้หน้านี้หรือ API ได้
บัญชีที่ได้รับสิทธิ์เลือกหน่วยงานต้นทางได้ทั้งโรงพยาบาล โดยยังต้องเลือกจากทะเบียนหน่วยงานจริง

1. ส่งออก CSV UTF-8 จาก Google Forms แบบ Medication Error
2. อัปโหลดไฟล์ไม่เกิน 5 MB และ 500 แถว แล้วตรวจตัวอย่าง
3. ตรวจวันที่ ระดับ A–I และเลือกหน่วยงาน สถานที่ เวรจากทะเบียนในระบบ
4. กรอกเวลาที่เกิดเหตุจริง เพราะไฟล์ต้นฉบับไม่มีช่องเวลาที่เกิดเหตุ
5. เลือกหัวข้อ Clinical NRLS ที่กำหนดโปรแกรมไว้แล้วจากทะเบียนในฐานข้อมูล
   สามารถค้นด้วยชื่อหรือรหัส และล้างคำค้นเพื่อดูทั้งหมด
6. เลือกแถวที่จะนำเข้าและยืนยัน ระบบแสดงรายการสำเร็จ ซ้ำ และไม่สำเร็จ

หนึ่งแถวสร้างหนึ่งอุบัติการณ์ แม้ระบุหลายประเภทความคลาดเคลื่อน โดยเก็บทุกประเภท
ชื่อยาที่ถูกต้อง/ผิด และรายละเอียดในข้อความอุบัติการณ์ และเก็บการแก้ไขเบื้องต้น
ในช่อง problem_basic ไม่มีการเพิ่มตารางหรือ migration

อุบัติการณ์เข้าสถานะรายงานและการจัดประเภท PENDING ตามขั้นตอนเดิม
ผู้รายงานในระบบและ created_by เป็นผู้ดำเนินการนำเข้า ไม่ใช้ชื่อใน CSV เดาเป็นสมาชิก
ชื่อผู้รายงานต้นฉบับเก็บใน note (จำกัดความยาวตามฐานข้อมูล)
รหัส NRLS และชื่อ snapshot ใช้กระบวนการสร้างอุบัติการณ์เดิม

ไม่เก็บช่องข้อมูลผู้ป่วย HN/AN/ชื่อ-นามสกุล และลิงก์รูปจาก CSV
รายละเอียดอิสระอาจมีข้อมูลระบุตัวผู้ป่วย ผู้ใช้งานต้องตรวจและลบออกจากไฟล์ก่อนนำเข้า
ไม่มีการส่ง Telegram จากการนำเข้าชุดข้อมูลนี้

ตรวจซ้ำด้วย SHA-256 ของค่าแต่ละช่องต้นฉบับ เก็บใน link_key ของอุบัติการณ์
การอัปโหลดซ้ำของข้อมูลเดิมและแถวซ้ำในไฟล์จะไม่สร้างรายการเพิ่ม
หากแก้ค่าในแถวเดิม fingerprint จะเปลี่ยน ต้องตรวจความซ้ำเชิงเหตุการณ์เอง
งานยืนยันเรียงคิวภายใน backend process เดียว จึงใช้กับการติดตั้งหนึ่ง process
ตาม systemd ปัจจุบัน การใช้งานหลาย instance ต้องเพิ่ม unique constraint/locking ก่อน

ตัวอย่างพักในหน่วยความจำผูกกับบัญชีและหมดอายุใน 30 นาที
อัปโหลดใหม่จะแทนตัวอย่างเดิมของบัญชี และเมื่อ backend restart ต้องอัปโหลดใหม่
หากบางรายการล้มเหลวสามารถลองอีกครั้งได้ ระบบตรวจ link_key ก่อนสร้างทุกครั้ง
การนำเข้าไม่ใช่ transaction ครอบทั้งไฟล์ รายการที่สำเร็จยังคงอยู่

การตรวจรับใน development ใช้ข้อมูลสมมติ: สิทธิ์ทุกบทบาท, ขอบเขตหน่วยงาน,
preview ของบัญชีอื่น, วันที่/เวลาที่ไม่ถูกต้อง, หัวคอลัมน์ซ้ำ, ข้อความหลายบรรทัด,
รายการซ้ำและการส่งพร้อมกัน รวมถึงการไม่ส่งข้อมูลไป Telegram
ห้ามใช้ข้อมูลผู้ป่วยจริงเป็น smoke test บน production
