# สรุปผลตรวจฐานข้อมูลโรงพยาบาลและคำแนะนำก่อนนำ RiskHRMS ขึ้นใช้งาน

วันที่สรุป: 25 สิงหาคม 2569 (2026)

## 1. วัตถุประสงค์ของเอกสาร

เอกสารนี้รวบรวมผลตรวจแบบอ่านอย่างเดียวจากฐานข้อมูล `riskhospital` ที่โรงพยาบาลใช้งาน เพื่อใช้เป็นข้อมูลประกอบการพัฒนาเว็บบนเครื่องส่วนตัว การจัดทำ staging และการวางแผนนำระบบ NRLS, RCA, Monitoring และ CAPA ขึ้นใช้งานในอนาคต

เอกสารนี้ไม่ใช่คำสั่งให้นำ migration ไปรันบนฐานข้อมูลจริง และระหว่างการตรวจยังไม่มีการแก้ไขข้อมูลหรือโครงสร้างฐานข้อมูลโรงพยาบาล

## 2. ข้อสรุปสำหรับการตัดสินใจ

สามารถพัฒนาและทดสอบเว็บบนเครื่องนี้ให้เสร็จก่อนได้ และเป็นแนวทางที่แนะนำ แต่ต้องแยกให้ชัดเจนระหว่าง:

- **Local development:** ใช้พัฒนาหน้าจอ สิทธิผู้ใช้งาน และทดสอบ flow ใหม่
- **Staging:** ต้องสร้างจากสำเนาฐานข้อมูลจริงและใช้ตรวจสอบความเข้ากันได้
- **Production:** ห้ามนำ Prisma migration ปัจจุบันไปรันตรง ๆ จนกว่าจะมี SQL deployment ที่รองรับ MariaDB 5.5 ผ่านการทดสอบและได้รับอนุมัติจาก IT/DBA

ฐานข้อมูลบนเครื่องส่วนตัวและฐานข้อมูลโรงพยาบาลมีโครงสร้างไม่เท่ากัน ระบบที่ทำงานได้บนเครื่องส่วนตัวจึงยังไม่ถือว่าพร้อมใช้งานบน production

## 3. ข้อมูลเซิร์ฟเวอร์ที่ตรวจพบ

| รายการ | ผลตรวจ |
|---|---|
| Hostname ที่ฐานข้อมูลรายงาน | `application` |
| ฐานข้อมูลที่เลือก | `riskhospital` |
| เวอร์ชัน | `5.5.63-MariaDB-wsrep` |
| ระบบปฏิบัติการฐานข้อมูล | Linux x86_64 |
| บัญชีที่ใช้ตรวจ | `wangchao@%` |
| `wsrep_on` | `OFF` |
| wsrep provider | `none` |
| wsrep cluster size | `0` |
| wsrep connected | ไม่ได้เชื่อม cluster |

ผลนี้ยืนยันว่า query ถูกเรียกกับฐานข้อมูล `riskhospital` บน host `application` ส่วนการยืนยันว่า host นี้เป็น production หลักหรือเป็นเครื่องประเภทอื่นต้องให้ฝ่าย IT โรงพยาบาลยืนยันอีกครั้ง

แม้ชื่อเวอร์ชันมีคำว่า `wsrep` แต่สถานะขณะตรวจไม่พบ Galera cluster ที่ทำงานอยู่ จึงไม่ควรวางแผนโดยสมมติว่ามี replication หรือ high availability

## 4. ค่าตั้งต้นฐานข้อมูลที่สำคัญ

| รายการ | ผลตรวจ | ความหมาย |
|---|---|---|
| `lower_case_table_names` | `1` | ชื่อตารางไม่ไวต่อตัวพิมพ์ใหญ่/เล็กในระดับเซิร์ฟเวอร์นี้ |
| `event_scheduler` | `OFF` | ห้ามพึ่ง database event สำหรับงานแจ้งเตือนหรือประมวลผลตามเวลา |
| `sql_mode` | `NO_AUTO_CREATE_USER,NO_ENGINE_SUBSTITUTION` | ไม่มี strict mode และไม่บังคับป้องกัน zero date |
| Database default charset/collation | `utf8` / `utf8_general_ci` | เป็นมาตรฐานเดิมของฐานข้อมูล |
| Server charset | `tis620` | ต่างจาก database และ connection ต้องระวังภาษาไทย |
| Connection charset ที่พบ | `utf8mb4` | ต้องทดสอบการแปลงตัวอักษรและ index บน MariaDB 5.5 |

ข้อเสนอแนะคือให้ application ระบุ connection charset ให้ชัดเจน ห้ามพึ่งค่าเริ่มต้นของ server และควรทดสอบข้อความภาษาไทยรวมถึงอักขระ 4-byte ใน staging

## 5. ตาราง Engine และ Collation

พบ BASE TABLE ทั้งหมด 43 ตาราง:

- MyISAM 31 ตาราง ประมาณ 31,761 แถว
- InnoDB 12 ตาราง ประมาณ 6,592 แถว
- `utf8_general_ci` 40 ตาราง
- `utf8_unicode_ci` 1 ตาราง คือ `social_account`
- `utf8mb4_unicode_ci` 2 ตาราง คือ `nine_standards` และ `risks`

ตารางระบบเดิมที่สำคัญและยังเป็น MyISAM ได้แก่:

- `risk` ประมาณ 4,838 แถว
- `riskregister` ประมาณ 4,866 แถว
- `riskreview` ประมาณ 4,203 แถว
- `riskstore` ประมาณ 526 แถว
- `department`, `program`, `team` และตาราง lookup เดิมอีกหลายรายการ

### ผลกระทบจาก MyISAM

- ไม่รองรับ transaction และ rollback แบบ InnoDB
- ไม่รองรับ foreign key
- การบันทึกหลายตารางอาจสำเร็จเพียงบางส่วนเมื่อเกิดข้อผิดพลาด
- คำสั่ง `ALTER TABLE` อาจ lock ตารางและกระทบระบบที่กำลังใช้งาน
- Prisma `$transaction` ไม่สามารถรับประกัน atomicity หากมีตาราง MyISAM อยู่ในชุดคำสั่ง

โค้ดระบบใหม่มี transaction ที่เกี่ยวข้องกับ Incident/RCA หลายจุด จึงต้องทดสอบกับ engine จริง ห้ามอาศัยผลจาก local ที่เป็น InnoDB เพียงอย่างเดียว

Collation ที่ต่างกันยังไม่ใช่ blocker หลักในขณะนี้ เพราะ 40 จาก 43 ตารางใช้ค่าเดียวกัน แต่ตารางใหม่ควรกำหนด charset/collation อย่างมีแผน และต้องตรวจข้อจำกัดความยาว index ของ `utf8mb4` บน MariaDB 5.5

## 6. Zero date และ Timestamp

พบคอลัมน์เดิมจำนวนหนึ่งที่มี default แบบ zero date เช่น `0000-00-00` หรือ `0000-00-00 00:00:00` แต่การตรวจข้อมูลจริงรวมประมาณ 15,591 แถวในตารางเป้าหมายไม่พบค่า zero date และไม่พบค่า `NULL` ในรายการที่ตรวจ

ข้อสรุป:

- ยังไม่ต้องทำ data cleanup สำหรับ zero date จากผลตรวจชุดนี้
- ก่อนเปิด strict mode หรือปรับชนิดคอลัมน์ต้องทดสอบกับสำเนาฐานข้อมูลจริง
- การแก้ `riskregister.modify_date` ต้องรักษาพฤติกรรมเดิม `ON UPDATE CURRENT_TIMESTAMP` หากระบบเดิมอาศัยคุณสมบัตินี้

## 8. ความเข้ากันได้ของเครื่องมือ

โครงการใช้ Prisma 5.22 แต่ฐานข้อมูลโรงพยาบาลเป็น MariaDB 5.5 ซึ่งอยู่นอกฐานรองรับของ Prisma รุ่นดังกล่าว ดังนั้น:

- Prisma schema ใช้เป็นแบบจำลองของระบบใหม่ได้
- ห้ามถือว่า SQL ที่ Prisma สร้างจะรองรับ production โดยอัตโนมัติ
- ต้องจัดทำ deployment SQL สำหรับ MariaDB 5.5 แยกต่างหาก
- ต้องทดสอบ query, index, foreign key, timestamp และ transaction บน staging ที่เหมือน production

Migration `20260824120000_nrls_rca_monitoring_capa` ในโครงการระบุไว้แล้วว่าใช้กับ local/staging เท่านั้น และห้ามใช้ตรงกับ MariaDB-wsrep 5.5 หรือ MyISAM production

## 9. ผลตรวจสิทธิผู้ใช้ฐานข้อมูล

บัญชี `wangchao@%` มี:

- `ALL PRIVILEGES ON *.*`
- `WITH GRANT OPTION`
- สิทธิครอบคลุมทุกฐานข้อมูลบนเซิร์ฟเวอร์
- สามารถสร้าง แก้ไข ลบโครงสร้าง และมอบสิทธิให้บัญชีอื่นได้

บัญชีนี้มีอำนาจเพียงพอสำหรับ deployment แต่มีความเสี่ยงสูงมากหากนำไปใช้เป็นบัญชีประจำของแอป

ข้อแนะนำด้านสิทธิ:

1. อย่าเพิ่งถอนหรือเปลี่ยนสิทธิจนกว่า IT จะตรวจว่าระบบเดิมใช้บัญชีนี้อยู่หรือไม่
2. แยกบัญชี application, deployment และ DBA
3. บัญชี application ควรมีเพียงสิทธิที่ต้องใช้กับ `riskhospital.*`
4. บัญชี deployment ใช้ชั่วคราวเฉพาะช่วงติดตั้ง
5. บัญชี DBA ควรจำกัด host ต้นทางและไม่ควรใช้ `%` หากไม่จำเป็น
6. Password hash ที่ export จาก `SHOW GRANTS` ถือเป็นข้อมูลลับ ไม่ควรเก็บใน repository หรือส่งต่อ

## 10. สิ่งที่ทำบนเครื่องส่วนตัวได้ก่อน

สามารถพัฒนาให้ flow ของเว็บเสร็จบนเครื่องนี้ได้ โดยเน้น:

1. Incident ใช้ NRLS เป็นข้อมูลจำแนกหลัก
2. การทบทวนของหน่วยงานและการส่งต่อทีม
3. ขอบเขตการมองเห็นตาม RM ส่วนกลาง, RM หน่วยงาน, หน่วยงานรอง และกลุ่มงานที่รับผิดชอบ
4. Team workspace สำหรับจัดการหลาย Incident และดู Risk Matrix ของทีม
5. เกณฑ์บังคับ RCA จาก backend จุดเดียว
6. RCA เชื่อมกับ NRLS และ Incident ทุกประเภท
7. CAPA ส่งต่อไป Monitoring พร้อมผู้รับผิดชอบและวันครบกำหนด
8. การแจ้งเตือนงานเกินกำหนด
9. Data quality queue สำหรับ mapping NRLS และ program mismatch
10. Audit log สำหรับการเปลี่ยน classification, RCA, CAPA และ workflow

### เงื่อนไขระหว่างพัฒนา Local

- เก็บ migration ใหม่ให้เป็น local/staging only จนกว่าจะผ่านแผน production
- หลีกเลี่ยง feature ที่พึ่ง database event scheduler
- ให้ backend/application เป็นผู้ทำ scheduled jobs
- ไม่เพิ่มข้อบังคับ `nrls_code NOT NULL` จนกว่าการย้ายข้อมูลเก่าจะเสร็จและได้รับอนุมัติ
- แยก configuration และ secrets ของ local/staging/production
- ทำ automated test สำหรับ permission scope และ workflow สำคัญ

## 11. ผลการย้ายข้อมูลที่ทำบน Local แล้ว

ผลนี้เป็นของฐานข้อมูล local เท่านั้น ไม่ใช่ฐานข้อมูลโรงพยาบาล:

- Incident เดิม 4,796 รายการ
- เติม NRLS แบบ deterministic สำเร็จ 4,404 รายการ
- เดิมมี NRLS อยู่แล้ว 6 รายการ
- เหลือข้อมูลเก่าที่ไม่มี NRLS 386 รายการ และกำหนดเป็น legacy ตามนโยบาย cutover
- พบ program mismatch 811 รายการและแยกไว้ตรวจทาน
- พบ severity incompatibility 530 รายการ
- ทดสอบ rollback ของ 4,404 รายการแล้วคืนข้อมูลได้ตรง baseline
- smoke test บนฐานข้อมูลสำเนาผ่าน flow Incident → Classification → RCA → CAPA → Monitoring → Close

ผล local แสดงว่าแนวทางระบบทำงานได้ แต่ไม่ใช่หลักฐานว่า deployment บน MariaDB 5.5 production จะสำเร็จ

## 12. แผนที่ควรทำหลังพัฒนาเว็บเสร็จ

### ระยะที่ 1: Freeze และตรวจ Local

- กำหนด feature scope ที่จะนำขึ้นรุ่นแรก
- รัน unit/integration/end-to-end tests
- ตรวจ schema.prisma กับโค้ดจริงว่าตารางและคอลัมน์ถูกใช้งานครบ
- สรุป migration dependency ตามลำดับ
- ตรวจข้อมูลสุขภาพและข้อมูลส่วนบุคคลไม่ให้รั่วใน log/report/notification

### ระยะที่ 2: เตรียม Staging จาก Production

- สำรอง production แบบครบ structure, data, routines และ events
- ทำสำเนาที่ลด/ปกปิดข้อมูลผู้ป่วยตามนโยบายโรงพยาบาล
- สร้าง staging ที่ใช้ MariaDB 5.5 และค่า config ใกล้ production
- ห้ามทดสอบ deployment ครั้งแรกบน production

### ระยะที่ 3: จัดทำ MariaDB 5.5-compatible deployment

- ทำ manual baseline สำหรับ schema เดิม
- สร้างตารางใหม่เป็น InnoDB ตาม dependency
- เพิ่มคอลัมน์และ index ในตารางเดิมเป็นลำดับ
- ตรวจ duplicate ก่อนสร้าง unique index
- ตรวจ index length/collation
- วางแผนการใช้ transaction ข้าม MyISAM/InnoDB
- ทำ verification SQL และ rollback SQL ทุกระยะ
- ทำสคริปต์ให้ rerun ได้อย่างปลอดภัยเท่าที่ทำได้

### ระยะที่ 4: Dry run และ Performance Test

- วัดเวลาของ `ALTER TABLE` กับข้อมูลสำเนาจริง
- ตรวจ table lock และ downtime ที่ต้องใช้
- ทดสอบ concurrent read/write ของระบบเดิม
- ทดสอบสิทธิทุก role และ scope
- ทดสอบ flow Incident → Review → Team → RCA → CAPA → Monitoring → Close
- เปรียบเทียบ row count และ checksum ก่อน/หลัง

### ระยะที่ 5: Production Cutover

- ขออนุมัติจาก RM, IT และ DBA
- สำรองข้อมูลก่อนเปลี่ยนแปลง
- กำหนด maintenance window
- หยุด write จากระบบเดิมตามความจำเป็น
- รัน deployment ทีละระยะพร้อม verification
- เปิดระบบแบบจำกัดผู้ใช้ก่อน
- เฝ้าระวัง error, latency, lock และข้อมูลค้าง
- เตรียม rollback decision point ที่ชัดเจน

## 13. ข้อห้ามก่อน Production

- ห้ามรัน `prisma migrate deploy` กับฐานข้อมูลโรงพยาบาลนี้โดยตรง
- ห้ามนำ migration สำหรับ local ไปรันโดยไม่แปลงและทดสอบ
- ห้าม mass-convert ทุกตารางจาก MyISAM เป็น InnoDB ในครั้งเดียว
- ห้ามเปลี่ยน charset/collation ทั้งฐานข้อมูลโดยไม่มี impact test
- ห้ามเปิด strict SQL mode ทันทีโดยไม่ทดสอบระบบเดิม
- ห้ามถอนสิทธิหรือเปลี่ยนรหัสบัญชีเดิมก่อนตรวจ dependency
- ห้ามบังคับ `nrls_code NOT NULL` ก่อนย้ายข้อมูลเก่าและกำหนด cutover production
- ห้ามส่งรายละเอียดผู้ป่วยหรือข้อมูลทางคลินิกเต็มรูปแบบผ่าน notification ภายนอก

## 14. ทางเลือกเชิงสถาปัตยกรรม

ทางเลือกที่แนะนำที่สุดคือใช้ฐานข้อมูลแยกบน MariaDB รุ่นที่รองรับสำหรับ service ใหม่ แล้วเชื่อม/ย้ายข้อมูลจากระบบเดิมอย่างควบคุม เพราะลดความเสี่ยงจาก MariaDB 5.5 และ MyISAM

หากยังต้องใช้ MariaDB 5.5 เดิม ให้ใช้แนวทาง compatibility deployment บน staging และพิจารณาแปลงเฉพาะตารางแกนหลักเป็น InnoDB หลังทดสอบว่าระบบเดิมได้รับผลกระทบหรือไม่

## 16. สถานะปัจจุบัน

- การตรวจ production: ทำแบบอ่านอย่างเดียวเสร็จในระดับเบื้องต้น
- การเปลี่ยนแปลง production: ยังไม่มี
- การพัฒนา local: ทำต่อได้
- ความพร้อมของ production schema: ยังไม่พร้อมสำหรับระบบใหม่
- ขั้นตอนถัดไปหลังเว็บเสร็จ: ทำ schema dependency inventory และจัดทำ deployment/verification/rollback SQL สำหรับ staging ที่จำลอง MariaDB 5.5
